# 小智对话通道（WebSocket）

[设备激活](xiaozhi-activation.zh_CN.md)结束时，设备手里只有一个 `wss://` 地址和一个
Bearer 令牌。本文规定它上面那一层：从 TLS 升级到服务端关闭会话为止的 WebSocket 对话通道。

本文既记录对外可观测的契约，也单独记录在真机上实测到的结果。实测是这份文档保持诚实的
原因：下面有三条结论无法从协议文档推导，只能靠观察一次真实会话得到。

## 范围

包含：

- 建连握手：请求头与 `hello` 往返；
- 本固件会响应的 JSON 控制消息；
- 音频参数，以及为什么两个方向不共用采样率；
- 服务端的保活帧；
- 会话状态机与实测到的超时；
- 在本板上把会话挂住所需要的堆开销。

不包含：

- 激活与配置交接。见[设备激活](xiaozhi-activation.zh_CN.md)；
- Wi-Fi 配网。见 [Wi-Fi 配网](wifi-provisioning.zh_CN.md)；
- 唤醒词、MCP 工具调用，以及二进制协议版本 2 与 3。本固件只实现协议版本 1，
  即直接发送裸 Opus 帧，靠 WebSocket 操作码区分音频与文本。

## 端点与身份

地址与令牌通过 `cyber_ota_get_ws_config()` 从 NVS 读取，因此每次建连都会重新读取，
而不是开机时抓一份。令牌轮换后不需要重启设备。

| 请求头 | 值 | 来源 |
| --- | --- | --- |
| `Authorization` | `Bearer <令牌>` | OTA 配置交接 |
| `Protocol-Version` | `1` | 与 `hello` 报体中的 `version` 一致 |
| `Device-Id` | Station MAC，小写十六进制 | `cyber_ota_get_device_mac()` |
| `Client-Id` | 每台设备生成一次的 UUID | `cyber_ota_get_client_id()` |

`Client-Id` 存放在 NVS，所以跨重启稳定，但擦除 NVS 后会改变。服务端把它当作软件身份，
因此擦除 NVS 在服务看来等同于换了一台新设备。

## 握手

1. 建立 TLS 连接，带上表中的请求头升级为 WebSocket。
2. 发送客户端 `hello`。
3. 等待服务端返回带 `session_id` 的 `hello`。

客户端必须在 10 秒内等到服务端 `hello`，超时后就把这次尝试判为失败。等得更久只会让界面
停在一个永远解不开的状态上。

客户端 `hello`，由 `cyber_ws_build_hello()` 构造：

```json
{
  "type": "hello",
  "version": 1,
  "transport": "websocket",
  "audio_params": {
    "format": "opus",
    "sample_rate": 16000,
    "channels": 1,
    "frame_duration": 60
  }
}
```

服务端 `hello`，实测样本：

```json
{
  "type": "hello",
  "transport": "websocket",
  "session_id": "64ad7344",
  "audio_params": {
    "format": "opus",
    "sample_rate": 24000,
    "channels": 1,
    "frame_duration": 60
  }
}
```

后续每条带会话标识的控制消息都要回填这个 `session_id`，所以拿到空的会话 id 属于握手
失败，而不是一个可以忽略的细节。

## 音频参数：两个方向并不相同

上行固定为 **16000 Hz、单声道、60 ms**，上面的请求里就是这么写的。下行不由我们决定：
服务端在自己的 `hello` 里声明，实测值是 **24000 Hz**。

这是预期行为，不是协商失败。上游协议文档写明服务端为了更好的音乐播放效果，下行音频可能
使用 24000 Hz，而自身采样率不同的设备应当在解码之后重采样。如果实现时假设两个方向共用
一个采样率，得到的链路会握手正常、然后播放出静音或杂音——这是本板上代价最高的一类缺陷，
因为日志里看不出任何异常。

音频通路必须与下面的帧算术一致：

| 方向 | 采样率 | 帧长 | 每帧样本数 | 每帧 PCM 字节数 |
| --- | --- | --- | --- | --- |
| 上行 | 16000 Hz | 60 ms | 960 | 1920 |
| 下行（实测） | 24000 Hz | 60 ms | 1440 | 2880 |

每帧样本数为 `采样率 / 1000 * 60`；16 位单声道下 PCM 字节数是它的两倍。如果服务端将来
声明了别的帧长，这些值必须重新推算，不能照抄。

## 服务端保活

服务端**每约 10 秒发送一个空文本帧**。协议文档没有定义它，所以"逐帧解析所有文本帧"的
实现会每分钟报十次解码失败。

它不是文档里那个应用层心跳。那个机制由设备发送 `{"type": "ping"}`、服务端回
`{"type": "pong"}`，且服务端默认关闭。空帧不需要回任何东西，实测中连续七次未回应的
保活都没有影响会话存活。

正确处理方式：把零长度文本帧当作空操作。

## 会话生命周期

本固件跟踪的服务端驱动状态，以及客户端发出的消息：

| 服务端消息 | 会话状态 | 客户端回应 |
| --- | --- | --- |
| `hello` | `READY` | 若说话键已被按下，补发 `state: start` 的 `listen` |
| `stt` | 不变 | 无；文本转为字幕 |
| `state: start` 的 `tts` | `SPEAKING` | 无 |
| `state: sentence_start` 的 `tts` | 不变 | 无；文本转为字幕 |
| `state: stop` 的 `tts` | `READY` | 无 |
| socket 关闭 | `IDLE` | 无；下次按说话键时重连 |

客户端消息：`listen`（`start` / `stop` / `detect`，配 `mode: manual`）、
`abort`（带 `user_interrupt` 之类的 reason）。

连接是**懒建连**的：在第一次说话请求时才开，而不是通道可用时就开。挂住一条会话要付出
约 8 KB 空闲堆加上 TLS 缓冲，而且服务端本来就会关掉空闲会话，所以空转的连接什么也换不来。

## 实测结果

板型：ESP32-C3、8 MB Flash、无 PSRAM、ESP-IDF 5.5.3。固件 `4e9dcb1` 加上 `hello`
诊断日志。凭证是激活端点返回的临时测试账号，端点为
`wss://api.tenclass.net/xiaozhi/v1/`。

| 测量项 | 结果 |
| --- | --- |
| TLS 握手加 WebSocket 升级 | 两次运行分别为 4.5 s 与 5.4 s |
| `hello` 往返 | 约 0.4 s |
| 按下说话键到 `READY` | 4.9 s 与 5.8 s |
| 保活间隔 | 10.1 s |
| 服务端声明的音频参数 | `opus` / 24000 Hz / 1 声道 / 60 ms |
| 会话 id | 8 位十六进制，例如 `64ad7344` |

使用临时测试令牌时握手被接受，服务端能识别设备，但会提示这次对话可能由共享的默认智能体
处理。因此用这套凭证得出的**回复质量**结论不可信，而**传输层**结论可信。

关闭行为：发出 `listen start` 后不跟任何音频帧，服务端在 **65.8 秒**后关闭了连接。改为
发送 `listen stop` 则会话存活超过 130 秒。可见服务端在给录音计时，音频通路必须远早于
这个窗口开始推流。

堆余量，同一次运行中测得：

| 时刻 | 空闲 | 最大块 |
| --- | --- | --- |
| Wi-Fi 就绪、通道尚未开启 | 126696 | 110592 |
| 通道已开启但未建连 | 123180 | 110592 |
| 拨号中、TLS 升级之前 | 114224 | 69632 |
| 会话期间 | 121560 | 69632 |
| 会话期间叠加一次 OTA 检查（最低点） | 32716 | 65536 |
| 拆链之后 | 120944 | 77824 |

最低点 32716 字节，就是"对话会话与 OTA 检查同时进行"时固件必须扛住的数字。这是本项目
迄今测得的最紧张的一个值，也是再增加一个并发 TLS 客户端之前必须对照的基准。

## 尚未验证的部分

传输、握手、保活与状态机都已在真机上验证。音频通路尚未实现，因此：

- 还没有端到端观察到过 `stt` 或 `tts` 消息，字幕渲染只被宿主测试覆盖过；
- 对一次零字节音频的 `listen` 周期，服务端什么都没返回，所以空录音不能当作真实录音的替代品；
- 24000 Hz 的下行采样率是从服务端声明中记录下来的。因为目前还没有解码器，它尚未与任何
  真实收到的音频帧核对过。
