# 小智服务激活与配置下发

接入 Wi-Fi 只是官方 xiaozhi.me 服务所需两层中的第一层。本文规定第二层：
**设备激活**（把设备绑定到用户账号），以及设备在打开对话通道之前必须完成的
**配置下发**。

这是一份规格，而非实现指南。它记录对外可观察的契约，以及该契约对这块板子施加的
约束，使实现能依据事实而非假设来编写。

## 范围

包含：

- OTA 检查与激活请求/响应契约；
- 激活状态机，以及必须向用户展示什么；
- 设备必须持久化的配置；
- 由此对一块无 PSRAM 的 ESP32-C3 板子施加的约束。

不包含：

- Wi-Fi 配网，那是第一层。见 [Wi-Fi 配网](wifi-provisioning.md)；
- 拿到配置之后的对话协议本身（WebSocket 音频帧与 JSON 控制消息）。
  见[小智对话通道](xiaozhi-conversation.zh_CN.md)；
- 自建服务端部署，其激活规则不同。

## 为什么需要激活

配置接口**只在设备绑定到账号之后**才返回对话设置（WebSocket 地址及其 token，
或 MQTT 凭证）。未绑定的设备收到的反而是内含六位激活码的 `activation` 对象。
在用户于 xiaozhi.me 控制台输入该码之前，设备拿不到对话端点，所以仅凭 Wi-Fi
关联成功并不足以与服务对话。

绑定保存在服务端并跨重启存活，因此每台设备只需输入一次激活码。若设备身份改变，
也就是 NVS 被擦除或 MAC 地址变化，就必须重新激活。

## 端点与身份

| 项目 | 取值 |
| --- | --- |
| 默认端点 | `https://api.tenclass.net/xiaozhi/ota/` |
| 端点覆盖 | NVS 命名空间 `wifi` 的 `ota_url` 键，缺失时回退到编译默认值 |
| 激活端点 | 检查端点后追加 `activate`（若检查 URL 未以 `/` 结尾则先补一个） |
| 传输 | 检查与激活使用 HTTPS；对话通道使用 `wss://` |

端点必须在运行时保持可配置，而不是编译写死，因为服务主机与部署类型都会随时间变化。

每次请求都携带的身份头：

| 头字段 | 取值 |
| --- | --- |
| `Device-Id` | 设备 MAC 地址 |
| `Client-Id` | 固件生成一次并持久化的每设备 UUID |
| `Activation-Version` | 存在 eFuse 序列号时为 `"2"`，否则为 `"1"` |
| `Serial-Number` | eFuse user-data 序列号，**仅当** `Activation-Version` 为 `"2"` 时发送 |
| `User-Agent` | 板子名称与固件版本 |
| `Accept-Language` | 设备语言偏好，例如 `zh-CN` |
| `Content-Type` | `application/json` |

### 本板使用激活版本 1

激活版本 2 通过 ESP32 HMAC 外设与 eFuse 密钥、并借助存放在 eFuse user-data 区的
序列号来对服务端 challenge 签名，从而把请求绑定到硬件。这需要出厂 eFuse 烧录。

本板**没有已烧录的 eFuse 序列号**，因此固件必须发送 `Activation-Version: 1`、
省略 `Serial-Number`，且绝不执行 HMAC challenge 步骤。所以版本 1 激活是更简单的
路径：显示激活码，等待用户绑定，并反复检查直到配置到达。

HMAC 步骤的门控是**有没有序列号，而不是有没有收到 challenge**。真实服务连本板也会
返回 `activation.challenge`（见下文的验证一节），而参考实现完全依据 eFuse 序列号来
构造其 HMAC 载荷，没有序列号时只会发送 `{}`。所以在本板上尝试该步骤只会 POST 一个
空载荷、什么也达不到；必须刻意跳过它，而不是凭 challenge 是否存在来触发。

## 检查请求契约

参考固件在有请求体时发送 `POST`，否则发送 `GET`；携带完整的系统信息体时，该调用为
`POST`。

```json
{
  "flash_size": 4194304,
  "minimum_free_heap_size": 150000,
  "mac_address": "aa:bb:cc:dd:ee:ff",
  "chip_model_name": "esp32c3",
  "chip_info": { "model": 5, "cores": 1, "revision": 3, "features": 0 },
  "application": { "name": "cyber-pixel-xiaozhi", "version": "0.1.0", "idf_version": "v5.5.3" },
  "partition_table": [],
  "ota": { "label": "factory" },
  "board": { "type": "cyber-pixel-xiaozhi", "mac": "aa:bb:cc:dd:ee:ff" }
}
```

> [!IMPORTANT]
> `Device-Id` 头与请求体内的 MAC 必须一致。实现该契约的服务端会以
> `Invalid OTA request` 拒绝不一致的请求，而这个错误极易被误读为 Wi-Fi 或 TLS
> 问题。让两者来自同一处来源，就无法相互漂移。

## 检查响应契约

每个字段都是可选的；固件必须能容忍任意子集。

| 顶层对象 | 含义 | 处理方式 |
| --- | --- | --- |
| `activation` | 设备尚未绑定 | 展示 `message` 与 `code`；见下文状态机 |
| `websocket` | 对话端点 | 持久化 `url` 与 `token`；设备需要它才能对话 |
| `mqtt` | 备选对话传输 | 按需持久化；使用 WebSocket 时并不可少 |
| `server_time` | 服务端时钟 | 依据 `timestamp` 与 `timezone_offset` 设置系统时间 |
| `firmware` | 固件升级邀约 | **对本板不适用；见下文约束** |

`activation` 对象自身：

| 字段 | 含义 |
| --- | --- |
| `message` | 给用户看的人类可读指引 |
| `code` | 用户在控制台输入的六位激活码 |
| `challenge` | HMAC 流程用的服务端随机数。服务端连版本 1 的设备也会返回它，因此**它的存在并不是要执行 HMAC 步骤的信号**；见下文 |
| `timeout_ms` | 激活码的服务端有效期，默认 30000 |

当 `websocket` 存在而 `activation` 不存在时，设备已绑定且已配置，可以打开对话通道。

## 激活状态机

1. **检查。** 携带身份头与请求体，`POST` 到检查端点。
2. **按响应分支。**
   - 存在 `websocket` 且无 `activation`：已绑定。持久化配置并结束。这是此后每次
     开机的正常稳态。
   - 存在 `activation.code`：未绑定。继续第 3 步。
   - 两者皆无：设备很可能拿到的是测试凭证而非绑定码。按独立失败处理；见下文风险。
3. **展示。** 渲染 `activation.message` 与 `activation.code`。激活码必须足够大且
   无歧义，因为用户要把它重新键入网页控制台。
4. **等待并复查。** 以有界间隔重跑检查，直到第 2 步报告已绑定，或激活码过期。
   `timeout_ms` 是服务端的有效期窗口，不是客户端的轮询间隔；客户端自选间隔，并且
   必须对总等待时长设上限，而不是无限轮询。
5. **本板跳过激活调用。** HMAC 步骤的门控是 eFuse 序列号，而不是 `challenge`，所以
   本板绝不向激活端点发请求。为完整起见，有序列号的设备会 `POST` HMAC 载荷，并按
   下方状态码解释结果。

激活状态码，为完整起见列出：

| 状态码 | 含义 |
| --- | --- |
| `200` | 激活已接受 |
| `202` | 仍在等待用户输入激活码；继续复查 |
| 其他 | 失败；记录响应体，其中带有服务端原因 |

### 本构建实际采用的轮询策略

第 4 步把轮询间隔与失败处置留给客户端。本构建在 `main/cyber_ota_util.h`（纯策略，
由宿主测试覆盖）与 `main/cyber_ota.c`（执行该策略的 worker）中选定如下：

| 情形 | 行为 | 理由 |
| --- | --- | --- |
| 等待用户绑定 | 相邻两次检查间隔 2s、4s、6s，之后稳定在 8s | 用户正站在设备前重输激活码；更快只是白耗电和流量，更慢则绑定完成后设备显得迟钝 |
| 已绑定，但服务端仍返回临时凭证 | 每 60s 复查一次 | 设备可用并进入主界面。比"已就绪"的 30 分钟更勤地复查，是为了跟上凭证切换、或用户刚在控制台做的解绑/换绑。刻意**不**计入网络失败 |
| 已就绪 | 每 30 分钟复查一次 | token 可能轮换，问得更勤没有意义 |
| 单次请求超时 | 10s | 限定一次卡住的 TLS 会话能把 worker 占多久 |
| 连续失败 | 达到 5 次后发布 `ERROR` 并停止轮询，等链路断开再恢复 | 对一块根本连不上服务端的设备无限重试只会耗电 |
| 链路断开 | 回到 `IDLE` 并丢弃屏幕上的激活码 | 否则一个已失效的码会一直留在屏幕上 |

间隔由一个**饱和**计数而非回绕计数推导。普通的 `uint8_t` 计数在第 255 次轮询后回绕，
会让算出的延时塌缩为 0，把轮询循环静默变成忙等。

> [!IMPORTANT]
> **第 4 步要求的总等待上限尚未实现。** 设备在线且未绑定期间会以 8s 间隔无限轮询。
> 理由是激活码以 MAC 地址为键、客户端侧不会过期，且未绑定的设备通常放在充电器上、
> 由用户完成设置。代价是只要设备保持未绑定，就大约每 8s 产生一次 TLS 会话，这是真实
> 的功耗与真实的服务端流量。既定方向是给快速间隔加上上限、随后回落到低频复查；此处
> 记录为**待办**，而不是悄悄略过。

### 激活屏文案由固件自己提供

屏幕不渲染服务端的 `activation.message`。它用一个专用的 48px 像素字体显示激活码、
一行简短状态标签，以及一句固定提示（`ENTER CODE AT XIAOZHI.ME`，在拿到码之前为
`WAITING FOR SERVER`）。状态标签是 `LINKING`、`WAIT FOR BIND`、`READY`、
`TEST ACCOUNT`、`NO LINK`、`LINK ERROR` 之一。

有两个后果值得记录。其一，显示不依赖服务端的本地化，因此本屏不需要中文字形，项目默认
字体即已足够。其二，激活码字体是刻意**取子集**的——只有空格、`-`、`:` 和数字——因为
48px 下的可打印 ASCII 约需 140 KB C 源码，而子集约 11 KB。其它字符会静默地什么也不
渲染，因此该字体绝不可用于正文。

## 对真实服务的验证

上文契约已通过向默认端点发送一次真实的检查请求得到确认，请求使用本板的 MAC 地址和
一个新生成的 `Client-Id`，以代表一块从未接触过该服务的设备。该请求没有创建任何绑定，
只是索取配置。

响应一次性包含了以下全部内容：

| 观察到的内容 | 解读 |
| --- | --- |
| 带六位数值的 `activation.code` | 服务**确实**会向本板的 `board.type` 提供绑定码。激活屏是一个可行的功能。 |
| 形如 `xiaozhi.me\n<code>` 的 `activation.message` | 服务端自己拼出了提示文本，并在其中重复了激活码。只渲染 `message` 里就已经含码。 |
| `activation.challenge` 存在 | 印证了 challenge 并不以 `Activation-Version` 为门控；见上文更正。 |
| `websocket.token` 为 `test-token`，且 `mqtt.client_id` 含 `GID_test` | 这些是**绑定前**的凭证。未绑定的设备会获得一个可用的临时账号，以便开箱即用。 |
| `firmware.url` 为空 | 没有提供升级，与"忽略 `firmware` 对象"一致。 |

关键澄清：**未绑定状态下**的 `GID_test` 与 `test-token` 是正常且预期的。只有在用户
绑定设备**之后**它们仍然存在，才表明出了问题，而那也是现场上报的情形。

### 由固件经 HTTPS 复现

随后由固件自身经 HTTPS（使用内置根证书包）走了同一套契约。由此浮现出三个桌面探测
无法显示的事实：

- **没有时钟也能通过证书校验。** 证书包报告证书已校验通过，印证了上文所述——缺少
  时间/日期支持在实践上不是问题。
- **激活码是按 MAC 地址绑定的，与 `Client-Id` 无关。** 一次桌面请求（携带全新生成的
  `Client-Id`）拿到的码，与固件后来（携带另一个 `Client-Id`）拿到的码完全相同，且该码
  在反复轮询中保持不变。因此持久化 `Client-Id` 关乎会话身份，而不关乎发放哪个码。
- **未绑定的设备会在同一个响应里同时收到绑定码和临时 WebSocket 凭证。** 这与"只要
  出现了 WebSocket 端点，设备就已绑定"这条直觉规则相矛盾。因此实际实现的规则是：只要
  `activation.code` 存在，就表示需要激活，无论有没有 WebSocket 对象；而 WebSocket
  对象在**没有**激活码的情况下出现，即判为已绑定。

后半句规则随后用桌面端对多个 MAC 直接验证过：

| MAC | 是否返回 `activation` | 说明 |
| --- | --- | --- |
| 本板（已绑定） | 否 | 只有 `websocket` 带 `test-token`，以及含 `GID_test` 的 `mqtt.client_id` |
| 服务端从未见过的 MAC | 是 | 六位 `code`，外加同样的临时凭证 |
| 另一个未见过的 MAC | 是 | 形状相同 |

服务端会向它没见过的设备下发绑定码，设备一旦绑定就不再下发。因此"没有被要求激活"就等于
"已绑定"，不存在既不说激活、又确实未绑定的响应。板型不是因素：用本板自定义的
`board.type` 与官方的 `bread-compact-wifi`、`esp-box-3` 分别重试，结果完全一致。

已绑定的设备仍可能只拿到临时凭证。这就是
[xiaozhi-esp32#1785](https://github.com/78/xiaozhi-esp32/issues/1785)，在本板上直接
观察到了：在控制台输入绑定码、控制台也列出该设备之后，后续每一次检查仍然只返回
`test-token` / `GID_test`，且不带 `activation`。把这种情况判成"未就绪"会让设备永远
停在激活页——因为真凭证永远不会到来——所以固件改为进入主界面，并把这个临时账号状态记进
日志。

早期实现先判断 WebSocket 对象，于是设备自信地报"就绪"、实际挂在临时账号上，激活码
永不显示。真机立刻暴露了这个缺陷；而只检查单个响应的桌面探测不可能发现它。该失效模式
仍然被防止，因为现在依旧先判 `activation.code`；被放弃的只是"把临时凭证当作阻塞"这一条。

本板（ESP32-C3，无 PSRAM）在 Wi-Fi、显示与 LVGL 均已运行时的实测数据：

| 时刻 | 空闲堆 | 最大连续块 |
| --- | --- | --- |
| TLS 请求前 | ~129 KB | 112 KB |
| TLS 会话峰值 | ~82 KB（低水位） | 88 KB |
| 客户端释放后 | ~132 KB | 88 KB |

因此一次 TLS 会话的峰值代价约 44 KB，且客户端释放后堆回到此前水平。真正决定后续音频
通路是否可行的是剩下的 88 KB 连续块。

在已观察的运行区间内，释放后的空闲堆与上一轮相差仅几百字节，符合分配噪声而非泄漏的
特征，但仍需一次更长时间的浸泡测试才能排除缓慢漂移。该检查记为**未完成**，而不是
假定通过。

## 必须持久化的配置

| 命名空间 | 内容 |
| --- | --- |
| 设备身份命名空间 | 生成的 `Client-Id` UUID，使其跨重启存活 |
| 对话命名空间 | `websocket.url`、`websocket.token`，以及服务端后续可能新增的其它 `websocket` 字段 |

持久化返回的 `websocket` 与 `mqtt` 对象的**每一个**字符串字段，而不是写死一个子集，
因为服务端可以随时新增键。只在检查成功之后写入配置，可避免一次失败的开机把可用配置
覆盖为空。

## 本板特定约束

这些是本仓库硬件与结构的后果，也是本规格比参考实现更重要的原因。

### 不要启用固件升级路径

本仓库的分区表刻意只包含 NVS、PHY 数据和一个 `factory` 应用。不存在第二个应用分区，
因此 `esp_ota_get_next_update_partition()` 返回 `NULL`，参考固件的升级例程无法运行。
固件必须忽略 `firmware` 对象，而不是据此行动。对它作出反应要么失败，要么在草率修改
分区表之后，冒覆盖正在运行镜像的风险。见[固件布局](firmware-layout.md)。

### 把 TLS 与 JSON 作为一项系统成本来预算

激活为一个已经在跑显示、解码器和 Wi-Fi 栈的固件增加了 HTTPS 客户端与 JSON 解析器。
在没有 PSRAM 的芯片上，失败模式是在总空闲堆看起来仍健康时，却凑不出一块足够大的
连续内存。JSON 解析容量应按可接受响应上限来确定，而不是按请求大小；并在解析前就
拒掉超大响应。
[网络音频串流与内存预算](../../reference/phoenixzhc/network-audio-streaming-and-memory.md)
中的测量纪律原样适用于激活客户端。

### 时钟与证书校验相互纠缠，但本构建里不成立

校验服务端证书通常需要正确的时钟，而在第一次成功检查之前，唯一可用的时钟来源就是
服务端本身。在本构建里这个问题不成立：ESP-IDF 默认**不**把时间/日期支持编进 mbedTLS
（`CONFIG_MBEDTLS_HAVE_TIME_DATE` 未设置），因此证书的有效期根本不会被检查。证书链与
签名校验仍然开启，所以证书依然要能对到内置的根证书集合上。

一旦为了强制证书有效期而打开该选项，这个约束立刻变为现实。把决定记录下来，
而不是在一台刚擦除的设备上把它重新发现成一次无法解释的 TLS 失败。

### 让网络工作远离 LVGL 任务

检查与激活调用会阻塞，必须放在 worker 任务里。LVGL 不是线程安全的，因此由结果驱动的
任何屏幕更新都必须在该锁的保护下转交到 LVGL 任务。激活屏是一个新屏幕，必须自己拥有
生命周期：它被删除后，不得有任何仍在运行、还能触碰它的东西。

### 激活屏属于新 UI

六位激活码需要大而清晰的渲染。这是应用自身视觉语言中的一个新屏幕，不是复用某个
演示屏。要在设备上验证所选字体在使用字号下确实含有数字字形，遵循
[中文字体与缺字](lvgl-chinese-fonts.md)。

## 已知风险与失败模式

| 现象 | 可能原因 | 处置 |
| --- | --- | --- |
| 始终不出现激活码，且需要申请解绑 | 设备已绑定到其它账号 | 通过 xiaozhi.me 申请解绑，这是以工作日计的人工步骤 |
| 绑定看似成功，但流量仍走共享的默认智能体 | `GID_test` / `test-token` 在绑定**之后**仍然存在 | 本板已实测到，属于 [#1785](https://github.com/78/xiaozhi-esp32/issues/1785) 的服务端缺陷。固件记录该状态并进入主界面，而不是把自己钉在激活页。要纠正账号侧，需要通过 xiaozhi.me 解绑后重新绑定 |
| `Invalid OTA request` | `Device-Id` 与请求体 MAC 不一致 | 让两者来自同一处来源 |
| 擦除后第一次调用即 TLS 握手失败 | 仅当 `CONFIG_MBEDTLS_HAVE_TIME_DATE` 被启用且没有可用时钟时才可能 | 保持默认（时间/日期关闭），或在首次调用前引入时间来源 |
| 用户已输入激活码却始终拿不到配置 | 绑定之后没有重复检查，或激活码已过期 | 确认复查循环与等待上限 |
| 固件更新后又被要求重新激活 | NVS 被擦除，或存储的 `Client-Id` 被重新生成 | 持久化 `Client-Id`；不要每次开机重新生成 |

## 实现前需要定论的问题

此处刻意记录而非猜测，因为它们会改变设计：

1. **自定义板型是否被接受 —— 已回答，但有一处保留。** 服务会为本板的 `board.type`
   返回 `activation.code`；该码已在控制台输入、控制台也列出了这台设备，因此自定义板型
   端到端是被接受的。保留之处在于：在那次真实绑定之后，设备后续每一次检查仍然只拿到
   临时 `test-token` 凭证（[#1785](https://github.com/78/xiaozhi-esp32/issues/1785)），
   所以账号专属的 `websocket.token` 始终未被观察到。这是服务端缺陷，不是板型被拒。
2. **客户端轮询节奏与总等待上限 —— 已部分解决。** 节奏已实现、已由宿主测试覆盖，并记录
   在上文"本构建实际采用的轮询策略"中。第 4 步要求的总等待上限**仍待办**；见该节的说明。
3. **证书与时钟引导 —— 已解决。** 本构建不检查证书有效期，因为 ESP-IDF 默认不包含
   时间/日期支持，所以不需要引导时钟。仅当该选项被启用时才需重新审视。
4. **激活屏的语言 —— 已解决。** 该屏渲染固件自有文案，而非服务端本地化的 `message`，
   因此显示不依赖服务端语言，也不需要中文字形。见上文"激活屏文案由固件自己提供"。
